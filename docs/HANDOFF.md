### 診断ロジック(`recommend()`、ルールベース)
各資格にスコアを付け、上位5件を選び、**そのあとレベル昇順に並べ替える**(同レベルはスコア順を維持)。

```
score = domainScore + levelFit + productBonus + roleAdjust + (domainScore > 0 ? 10 : 0)

domainScore : needs の j 番目(0始まり)が資格の domains の i 番目と一致したら
              W[j] * (i == 0 ? 1.0 : 0.7) を加算。W = [4, 3]
levelFit    : 2 - 1.3 * |cert.lv - exp|
productBonus: 資格の関連製品とユーザーの利用製品が1つでも一致したら +1.2
roleAdjust  : dev 向け資格 → 開発者 +1.5 / それ以外 -1.5
              sre かつ domains に auto → +0.6
              mgr・other かつ lv <= 2 → +1.0
              legacy フラグ → -1.5
同点: |gap| の小さい順 → 試験コード順
```
結果カードの「おすすめ理由」チップは、領域一致・レベル(一致/次のステップ/基礎の確認)・利用中の製品から作る。

- ilt・self・team には「学び放題を無料で試す」も併記。資格一覧(`lab8010.github.io/redhat-certifications-list/`)へのリンクも常に出す。

## 4. 資格データ

- 元データ: `Lab8010/redhat-certifications-list` の `certifications.json`。公開URLは `https://lab8010.github.io/redhat-certifications-list/data/certifications.json`
- `data/certifications.snapshot.json` に、プロトタイプで使った31件(現役のみ)を保存済み
- 除外したもの: status が Retired の EX260, EX229, EX480, EX221, EX240, EX482
- 元データは `Level 100〜400`、`category`(RHEL / Ansible / OpenShift / Cloud-Native)、`tags`、`training_course`、`url_ja` などを持つ。プロトタイプは、それとは別に次を手作業で付与している
  - `d`: 領域(cn / linux / virt / auto / ai / sec)。先頭が主領域
  - `p`: 関連製品(rhel / ocp / virt / aap / ai / other)
  - `dev`: 開発者向けか / `legacy`: 優先度を下げるか
- 領域の付与は、`tags` と `category` から機械的に決まらない(例: EX380 は cn と auto、EX362 は linux と sec)。**同期スクリプトを作る場合は、領域マップを別ファイルで管理し、新しい資格が来たら未割当として警告すること**
- EX342 は、元データの `title` と試験コード・URLが一致していない。プロトタイプは URL に合わせて「Specialist in Linux Diagnostics and Troubleshooting」と表示している。**元リポジトリの修正をオーナー(Lab8010)に確認すること**
- EX210(OpenStack)、EX183(Java EE)、EX248(JBoss)は領域を持たず、補欠枠でのみ出る

## 5. プライバシー・セキュリティ方針(必須)

1. アプリは個人情報を取得・保存・送信しない。氏名、メール、会社名、電話、IPアドレス、端末ID、Cookie ID を含む。
2. 分析SDK、広告タグ、外部フォント以外の外部読み込みを入れない(フォントはできれば自己ホスト)。
3. 個人情報は、会社承認の Google Forms だけで取る。アプリは Forms へのリンクとQRコードを出すだけ。
4. Forms への事前入力は、個人を特定しない情報だけ(例: 最初の一歩の資格コード、必要な領域)。匿名データと Forms 回答を結ぶ ID は渡さない。結ぶ必要が出たら、セキュリティ部門と先に相談する。
5. 回答の保存先は、会社のセキュリティ部門の承認を取ってから決める(下の案を参照)。
6. 共用タブレットに回答を残さない。端末内に保存する場合は匿名の回答のみとし、スタッフ画面で削除できること。
7. スタッフ画面は、サーバ側で認証する(クライアントの PIN だけに頼らない)。

## 7. 実装タスク(この順で進める)

各タスクの前に、短い計画を出して確認を取ること。

### T1. プロジェクトの土台
- Vite + TypeScript(フレームワークなし、または Preact)で再構成する。`index.html` の見た目と挙動は変えない。
- 診断ロジック(`recommend()`)、集計(`agg()`)、CSV出力を、画面から分けた純粋関数のモジュールにする。
- Vitest でテストを書く。最低限のケース:
  - 領域 cn・レベル2: EX180, EX188, EX280, EX370, EX380 の順
  - 領域 virt+auto・レベル3・OpenShift 利用: EX156, EX336, EX316, EX380, EX374 の順
  - 領域 cn・レベル1・開発者: EX180, EX188, EX288, EX328, EX378 の順
  - 常に5件で、レベルが昇順になる
- GitHub Pages へ GitHub Actions でデプロイする。

### T2. 個人情報の取得を外す(最優先)
- 結果画面のメール入力と同意チェックを削除する。localStorage の `email` / `emailAddr` も削除する。
- 代わりに「結果とご案内をメールで受け取る」ボタンとQRコードを出す。Forms を別タブで開く。
- Forms の URL と `entry.xxxx` は `src/config.ts` に分離する。
- QRコードはクライアントで生成する(外部のQR生成サービスは使わない)。
- スタッフ画面のメール登録数は、Forms 側で見る形にする。アプリは「Forms を開いた人」だけ数える。

### T3. 資格データの分離
- `data/certs.json` を単一の情報源にする。UI への埋め込みをやめる。
- `scripts/sync-certs.mjs` で、公開URLの元データから取得し、領域マップ(`data/domain-map.json`)を当てて `certs.json` を生成する。未割当の資格は警告する。

### T4. 保存層
- 未決事項の保存先が決まるまでは、`Storage` インターフェース(`save` / `list` / `patch` / `clear`)を切り、localStorage 実装だけを残す。
- 案A を選んだ場合: Cloudflare Workers + D1。保存するのは匿名の回答のみ。IP・User-Agent は保存しない。レート制限と、スタッフ画面の認証(サーバ側のトークン)を入れる。

### T5. 会場運用
- PWA にして、オフラインでも動作し、回答はローカルに溜めて再接続後に送る。
- iPad のガイドアクセスなどのキオスク運用手順を書く(`docs/RUNBOOK.md`)。
- タブレット(横)とスマホ(縦)で表示確認する。
- リハーサル用に、サンプルデータの投入と削除を安全にできるようにする。

## 8. 受け入れ基準

- 回答開始から結果表示まで、慣れた人で60秒以内。
- 個人情報が、アプリの保存データ・通信・ログのどこにもない。
- 診断ロジックのテストが全て通る。
- ライト/ダークの両方で、コントラストと操作性に問題がない。
- 回線が切れても回答でき、再接続後に失われない(保存先を決めた場合)。
